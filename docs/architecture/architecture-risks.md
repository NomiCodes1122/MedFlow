# MedFlow Architectural Risks & Mitigation Strategies

This document analyzes the primary architectural, operational, and technical risks inherent to the MedFlow distributed emergency platform. Each risk is evaluated with concrete severity metrics, preemptive mitigations, and runtime fallback mechanisms.

---

## 1. Comprehensive Risk Analysis Matrix

| # | Identified Architectural Risk | Severity / Impact | Likelihood | Preemptive Mitigation in MedFlow Architecture | Graceful Fallback & Degradation Strategy |
| :- | :--- | :---: | :---: | :--- | :--- |
| **1** | **Offline Conflict Complexity & Clinical Overwrite** | **HIGH** | **HIGH** | Reject blind "Last-Write-Wins". Implement append-only event streams for vital sign observations and triage evaluations. Demographics and profiles use Optimistic Concurrency Control (OCC) with integer versions. | If an OCC version collision occurs, operation is marked `CONFLICT` in outbox, preserving local draft while loading current server state for side-by-side reconciliation. |
| **2** | **Duplicate Sync Operations on Network Flapping** | **HIGH** | **HIGH** | Every outbox mutation is tagged with an immutable client UUIDv4 (`operationId`) acting as an Idempotency Key. Express API checks `sync_history` in Supabase PostgreSQL inside an ACID transaction before applying mutations. | If a duplicate arrives, the server returns the cached `response_payload` with status `DUPLICATE_IGNORED`; client marks outbox item `SYNCED` without repeating side effects. |
| **3** | **Concurrent Inventory Depletion Race Conditions** | **HIGH** | **HIGH** | Enforce Optimistic Concurrency Control (`version` integer) and database-level row locking (`SELECT ... FOR UPDATE`) in Supabase PostgreSQL transactions via Prisma. | Server returns HTTP 409 Conflict with latest stock count; Web and Mobile UIs display the updated quantity and prompt the user to re-apply the delta. |
| **4** | **Stale or Out-of-Order Real-Time Socket Events** | **MEDIUM** | **HIGH** | Every realtime event payload carries a monotonically increasing entity `version` and UTC timestamp. Clients use Socket.IO as an invalidation hook (TanStack Query) rather than patching state blindly. | If `event.version <= cached.version`, the client silently discards the packet. If a sequence gap is detected, client triggers an authoritative REST fetch from Express. |
| **5** | **Firebase Auth Token Expiration During Sync Batch** | **HIGH** | **MEDIUM** | Pre-flight token expiration check before dispatching outbox batches. If token expires within 60 seconds, mobile app automatically triggers token refresh via SecureStore before sending batch. | If HTTP 401 is returned mid-sync, the sync worker pauses, refreshes the session, and re-submits the exact same batch without incrementing retry counts. |
| **6** | **Mapbox Quota / Network Failure in Disaster Zone** | **MEDIUM** | **MEDIUM** | Mobile app pre-caches vector tiles for the local metropolitan bounding box. Vector layers use offline tile packs. | If Mapbox API fails, fallback to simplified offline schematic map with straight-line distance, bearing indicators, and offline native coordinates. |
| **7** | **Large Media Upload Timeouts on Degraded Cellular** | **MEDIUM** | **HIGH** | Client-side image compression (JPEG 75%, max width 1600px, < 800KB); audio restricted to AAC/M4A 64kbps (< 500KB). Direct chunked uploads to Firebase Storage bypass API server. | Binary uploads are decoupled from patient metadata. Patient record syncs immediately; photos/audio remain in local media queue and retry in the background. |
| **8** | **Supabase Availability & Network Interruption** | **HIGH** | **LOW** | Express API wraps database interactions in retry loops where safe; connection pooling configured via Supabase Supavisor/PgBouncer. Mobile clients operate completely offline via SQLite. | If Supabase is temporarily unreachable, mobile field operations continue without interruption (local drafts, vitals, START triage). Express API returns HTTP 503 (`Retry-After: 5`); mobile outbox buffers operations safely until restored. |
| **9** | **Redis Cloud Outage / Disconnection** | **HIGH** | **LOW** | Redis Cloud is strictly an ephemeral cache and Socket.IO pub/sub broker (never authoritative SoR). Supabase PostgreSQL holds all persistent business state. | Sockets degrade to single-node memory adapter; live telemetry falls back to periodic PostgreSQL updates; API rate limits degrade to in-memory sliding counters. **Zero loss of core business records.** |
| **10** | **EAS Cloud Build Queue Delays / Dependency Issues** | **MEDIUM** | **LOW** | Mobile project uses pinned dependencies in `package.json` and strict `eas.json` build profiles. Development builds are pre-compiled and installed on test/demo devices well before live demonstration. Android Studio and Android SDK are not local development requirements. | Pre-built development builds installed on demo devices; Expo dev-client allows updating JS bundles over the air (EAS Update) without triggering full native cloud rebuilds. |
| **11** | **Supabase Connection Pool Exhaustion on Sync Spikes** | **HIGH** | **MEDIUM** | Use Supabase pooled connection string (`pgbouncer=true` on port 6543) with strict pool limits. Fast transactional queries (< 20ms) prevent long connection holds. | Express rejects excess traffic with HTTP 503 and `Retry-After: 5` header; mobile sync engine respects backoff and retries safely without dropping records. |
| **12** | **Mobile SQLite Growth & Memory Leaks on Low-End Phones** | **MEDIUM** | **MEDIUM** | SQLite schema automatically purges acknowledged `SYNCED` outbox operations older than 7 days. Heavy media files are moved out of app memory to filesystem cache. | Background vacuum task triggers on app launch; low-storage alerts prompt paramedic to prune cached media. |
| **13** | **FCM Push Notification Drop for Critical Alerts** | **HIGH** | **MEDIUM** | Push notifications are treated as best-effort alerts. The mobile app establishes a persistent WebSocket connection while active and polls priority alerts every 30s. | Dual-channel notification: high-priority alerts are delivered via FCM AND broadcast via Socket.IO; if FCM drops, in-app WebSocket delivers the alert instantly. |
| **14** | **Audit Log Table Bloat & Degrading Query Latency** | **LOW** | **LOW** | B-Tree indexing on `(timestamp, actorId, entityType)`. Export engine uses Node.js streaming cursors (`pg-query-stream`) to avoid loading millions of rows into memory. | PostgreSQL partition by month (`PARTITION BY RANGE (timestamp)`) ensures queries only scan active partitions. |

## 2. Risk Mitigation Verification Architecture

To validate that these architectural mitigations function under crisis conditions, the test suite (`Phase 21: Failure/Chaos Testing`) incorporates automated resilience tests:
1. **Network Chaos Simulation**: Automated test runs cycling the network interface down for 60 seconds while submitting 50 patient records.
2. **Double-Submission Race Test**: 10 concurrent requests submitting identical `operationId` to verify single-execution semantics.
3. **Optimistic Locking Stress Test**: 20 concurrent PATCH requests against an inventory item with `quantity: 10`, verifying exact decrement to 0 without negative balances or lost updates.
4. **Redis Cloud Failure Simulation**: Severing the Redis connection during active load to ensure Express API gracefully falls back and Supabase PostgreSQL data remains unaffected.
